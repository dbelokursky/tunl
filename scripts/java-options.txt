# JVM options for the packaged launcher, read by the three packaging scripts
# (package-dmg.sh, package-linux.sh, package-windows.ps1), by write-jvm-args.*
# for development runs and by the three installer smoke checks, so the heap a
# user's Tunl gets is the heap a developer sees and the one CI verifies.
# Per-build values (-Dapp.version) and per-platform ones
# (-Djava.awt.headless=false on Linux) stay in the scripts.
#
# Without these the JVM sizes the heap from physical memory: an initial heap of
# 1/64 and a maximum of 1/4 of RAM, 576 MB and 9 GB on a 36 GB Mac. G1 returns
# committed memory only after a full GC or at the end of a concurrent mark, and
# under steady allocation it grows back to the initial size. Measured on
# 2026-09-13 after two days of uptime: the heap held all 576 MB for about 60 MB
# of live data, 685 MB of a 1.2 GB footprint; a forced full GC shrank it to
# 272 MB, and 27 minutes later it was back at 576 MB.
#
# A small fixed minimum on its own is a trap. Once live data passes the level
# at which G1 starts marking (45 % of the heap), a busy app runs a concurrent
# cycle every couple of seconds: replaying the app's allocation profile at
# 30 MB/s, -Xms32m and -Xms128m both did, about 100 cycles in four minutes.
# MinHeapFreeRatio keeps the heap above that level however far the live data
# grows, which a fixed -Xms cannot.
#
# JDK 27 changed G1's defaults for MinHeapFreeRatio and MaxHeapFreeRatio from
# 40 and 70 to 0 and 100, and at 100 G1 never shrinks the heap, not even after
# a full GC. These options named only the minimum, so from the move to JDK 27
# on nothing was given back: on 2026-09-28 an instance five hours up held all
# 512 MB for 46 MB of live data. The periodic concurrent cycle made it worse.
# G1 now sizes the heap by the CPU it spends on GC, and it counts a cycle's
# concurrent CPU against the short gap since the last pause, so an idle JVM
# reads 17-20 % and grows: 185 to 497 MB in two minutes with 12 MB live and a
# 5 s period. A periodic full GC has no concurrent phase to misread, compacts,
# and applies both ratios. At 40 MB live it pauses for 17-30 ms, once for each
# minute in which nothing else collected. JvmOptionsHeapTest runs these
# options and fails if the heap no longer comes back down.
#
# One option per line (an option and its value stay on the same line);
# everything after a '#' is a comment.

-Xms64m                             # start small; the heap grows when the app needs it
-Xmx512m                            # about eight times today's live data, and a ceiling for a leak
-XX:MinHeapFreeRatio=60             # after a full GC keep 60 % free: heap >= 2.5x live, no marking storms
-XX:MaxHeapFreeRatio=70             # ...and at most 70 %: JDK 27's default of 100 never shrinks the heap
-XX:G1PeriodicGCInterval=60000      # a minute without any GC runs a GC that gives memory back
-XX:-G1PeriodicGCInvokesConcurrent  # ...as a full GC, not a concurrent cycle G1 reads as GC pressure

# Each of the JDK's HTTP clients has a selector thread that wakes every 3 s
# while it has nothing to do. The app keeps up to nine clients (subscriptions,
# the updater, the country list, the core's control API, the monitors), so an
# app sitting in the tray woke up to three times a second for nothing. The
# selector waits for the nearer of a request's next deadline and this ceiling
# (JDK 27's HttpClientImpl.SelectorManager), so a request still times out on
# time.
-Djdk.internal.httpclient.selectorTimeout=60000   # an idle selector wakes once a minute
